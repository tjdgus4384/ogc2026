# 실험 후보 (v5.3 기준)

`builds/`는 무시되는 스크래치 빌드 영역이다. 측정에 올린 후보의 **소스 델타만**
여기에 패치로 고정한다. 채택되면 `solver/`로 올라간다.

기준선 `builds/b53` = 제출 zip 압축해제본. 같은 플래그로 재빌드하면 출하 `.so`와
**바이트 동일**(`6c600758…`)이므로 후보와 제출본의 차이는 아래 패치가 전부다.

빌드 `sbatch -p titan tools/build_variant.sbatch builds/<name>`
판정 `python3 tools/abgate.py submit <tag> --base builds/b53 --cand builds/<name>`

## 근본 결함: 같은 날 이벤트 순서

체커는 Stage 2에서 `present_at_entry = {b : b.entry < entry < b.exit}`로 같은 날
진입을 **제외**하고, 순서는 Stage 5가 **나열된 하나의 순서**로만 검증한다. 커널의
rule 2/4는 **모든 순서**가 가능할 것을 요구했다(진입의 64~74%가 해당).
퇴출 쪽은 rule 3/5의 타이브레이크가 진입일뿐이라 **진입일·퇴출일이 모두 같은 쌍**이
서로의 present 집합에서 빠져 검사되지 않았다(출하 보드에 21~44쌍).

m7은 rule 2a=Stage 2, rule 2b=배치 차단 그래프의 비순환성(위상정렬)으로 대응하고,
커널이 검증한 순서를 `entry_ranks()`로 방출기에 넘긴다. 빠른 경로(“A가 배치 전원을
통과하면 마지막에 넣으면 된다” = 기존 규칙)로 오늘 통과하는 배치는 동일 비용.
